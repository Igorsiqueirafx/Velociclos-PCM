### 2.2 Criar Tabela `profiles`

**Problema:** `auth.users` do Supabase não deve ser acessado diretamente pelo
frontend. Precisamos de uma camada de perfis com RLS.

**Arquivo:** `.kilo/queries/create-profiles-table.sql` (novo)

**Schema:**
```sql
create table public.profiles (
  id uuid references auth.users on delete cascade primary key,
  email text unique not null,
  full_name text,
  avatar_url text,
  role text check (role in ('user', 'admin')) default 'user',
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);

-- Trigger para auto-criar profile
create function public.handle_new_user()
returns trigger language plpgsql security definer as $$
begin
  insert into public.profiles (id, email, full_name, avatar_url)
  values (new.id, new.email, new.raw_user_meta_data->>'full_name', new.raw_user_meta_data->>'avatar_url');
  return new;
end;
$$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();

-- RLS
alter table public.profiles enable row level security;
create policy "Users view own profile" on public.profiles
  for select using (auth.uid() = id);
create policy "Service role manages all" on public.profiles
  for all using (auth.jwt() ->> 'role') = 'service_role';
```

**Validação:** Executar no Supabase SQL Editor, confirmar tabela + trigger

### 2.3 Atualizar Backend para Usar Supabase Auth

**Problema:** Backend ainda usa `ADMIN_PASSWORD` (Bearer token hardcoded).
Precisa migrar para validação de JWT do Supabase.

**Arquivo:** `backend/server.js`

**Mudanças:**
- Remover middleware `authenticate` baseado em `ADMIN_PASSWORD`
- Implementar middleware `requireAuth` que valida `Authorization: Bearer <token>`
- Usar `supabase.auth.getUser(token)` para validar
- Verificar `profiles.role = 'admin'` para endpoints protegidos
- Manter `/api/health` e `/api/courses` públicos

**Alternativa mais simples:** Se o backend não precisa ser acessado diretamente
pelo frontend (pois o Next.js já tem Server Actions), considerar remover a
auth do backend e confiar apenas no Next.js middleware + RLS.

**Recomendação:** Manter backend auth por segurança em caso de acesso direto à
API, mas simplificar para JWT validation apenas.

**Arquivo:** `.kilo/queries/create-leads-table.sql` (novo)

```sql
create table public.leads (
  id uuid primary key default gen_random_uuid(),
  email text not null,
  source text not null default 'lead-capture',
  utm_source text,
  utm_medium text,
  utm_campaign text,
  utm_content text,
  utm_term text,
  landing_page text,
  ip_address text,
  user_agent text,
  profile_id uuid references public.profiles(id) on delete set null,
  converted_at timestamptz,
  created_at timestamptz default now()
);

create index idx_leads_email on public.leads(email);
create index idx_leads_created_at on public.leads(created_at desc);

alter table public.leads enable row level security;
create policy "Service role manages all leads" on public.leads
  for all using (auth.jwt() ->> 'role') = 'service_role';
create policy "Public can insert leads" on public.leads
  for insert with check (true);
```

### 3.2 Criar API Route `/api/lead`

API route para capturar metadados (UTM, IP, user-agent) antes de inserir.

**Arquivo:** `frontend/app/api/lead/route.ts` (novo)

**Lógica:**
1. POST recebe `{ email, source?, utm? }`
2. Extrai IP do header `x-forwarded-for`
3. Extrai user-agent do header
4. Extrai UTM params da URL search
5. Insere em `leads` com todos os metadados
6. Retorna JSON `{ success: true }` ou `{ error: '...' }`

| Risco | Probabilidade | Impacto | Mitigação |
|--------|---------------|---------|-----------|
| Google OAuth redirect mismatch | Alta | Alto | Usar URL exata no Supabase; testar em dev antes |
| Cold start Railway (backend lento) | Média | Médio | Cache no Next.js; fallback para YouTube API direto |
